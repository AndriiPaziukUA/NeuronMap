# Власне оформлення головного вікна

## Межі реалізації

На Windows головне вікно використовує JavaFX `StageStyle.UNDECORATED` і власну смугу заголовка. Поточний корінь сцени редактора вкладається в `view/window/WindowChromeView`; сам редактор, його контролери та життєвий цикл не залежать від Win32.

`windowing/WindowPlatformAdapter` визначає платформний контракт, а `WindowPlatformAdapterFactory` вибирає реалізацію за `os.name`. На Windows працює `WindowsWindowPlatformAdapter`; на macOS і Linux зараз залишається стандартне системне оформлення. Для майбутніх платформ можна додати нову реалізацію адаптера й зареєструвати її у фабриці, не змінюючи `MainWindowController` або редактор.

Створення `WindowsWindowPlatformAdapter` не завантажує `user32`. Нативна прив'язка через JNA створюється лише всередині `install(...)` після перевірки показаного `Stage`, коли адаптер справді під'єднується до Windows-вікна. Тому фабрика може перевіряти вибір Windows-платформи на Linux або macOS без спроби завантажити Windows-бібліотеку.

## Збереження нативної поведінки Windows

Адаптер працює з HWND показаного Stage через JNA й не використовує внутрішні або інкапсульовані API JavaFX. Він прибирає стиль системного заголовка, залишаючи нативні стилі системного меню, мінімізації, максимізації та зміни розміру. Для `WM_NCCALCSIZE` клієнтська область займає весь прямокутник вікна. Для `WM_NCHITTEST` повертаються нативні коди Windows:

- `HTCAPTION` — вільна область заголовка, тому Windows керує перетягуванням і системним прилипанням;
- `HTMAXBUTTON` — кнопка максимізації/відновлення, потрібна для меню Snap Layouts у Windows 11;
- `HTMINBUTTON` і `HTCLOSE` — кнопки згортання та закриття;
- `HTLEFT`, `HTRIGHT`, `HTTOP`, `HTBOTTOM` і коди кутів — штатна зміна розміру й системний курсор.

Обробник нативних повідомлень передає решту повідомлень початковій процедурі вікна JavaFX Glass. Нативні команди кнопок делегуються до `MainWindowController`, щоб зберегти один шлях роботи з `Stage` та завершення редактора. Розмір і позиція й надалі зберігаються через наявний `WindowStateStore`.

Доступні назви кнопок беруться з локалізованих ресурсів `src/main/resources/i18n/windowChrome*.properties` і оновлюються разом з активною мовою через спільну `LocalizationService`. Власні JavaFX `Tooltip` на кнопках не встановлюються, щоб не конфліктувати з нативними підказками Windows. `WindowChromeView.dispose()` відписує слухачів під час закриття, щоб не утримувати вікно після завершення.

`WindowHitTestCalculator` не залежить від JavaFX і JNA. Його геометрія передається через незмінний знімок, який безпечно читається нативним callback-ом. Цей клас містить правила визначення кнопок, заголовка, клієнтської області й зон resize та перевіряється звичайними unit-тестами.

Якщо під'єднання Win32 не вдається, застосунок записує попередження й переходить на `JavaFxWindowPlatformAdapter` із переміщенням і ручною зміною розміру. Це резервний режим, а не повний еквівалент нативної поведінки: нативні Snap Layouts і всі ефекти Windows у ньому не гарантовані. На macOS і Linux власний заголовок наразі не вмикається.

## Перевірка на Windows

Після додавання залежностей JNA запустіть повний набір тестів, а потім застосунок на Windows 10/11. Вручну перевірте згортання/відновлення, закриття, подвійне клацання по заголовку, перетягування на інший монітор, прилипання до кожного краю, Snap Layouts наведенням на кнопку максимізації, resize кожного краю й кута, максимізацію подвійним клацанням, а також збереження геометрії під час завершення. Особливо перевірте конфігурації масштабування екрана (100%, 125%, 150%) і вікна на кількох моніторах.
