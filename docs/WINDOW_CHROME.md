# Власне оформлення головного вікна

## Межі реалізації

На Windows головне вікно використовує JavaFX `StageStyle.UNDECORATED` і власну смугу заголовка. Поточний корінь сцени редактора вкладається в `view/window/WindowChromeView`; саме подання реалізує контракт `window/WindowChrome`, не залежачи від платформної інтеграції.

Пакет `window` містить платформонезалежні типи геометрії (`WindowHitTestCalculator`, `Layout`, `Rectangle`, `HitTarget`) і контракт команд `WindowChrome`. Він не залежить від JavaFX, `windowing` або Win32. Пакет `windowing` залежить від цього контракту та відповідає за інтеграцію з операційною системою. Коди hit-test Win32 зіставляє окремий `Win32HitTestCode`, тому семантичні області не зберігають нативних числових кодів.

`windowing/WindowPlatformAdapter` визначає платформний контракт, а `WindowPlatformAdapterFactory` вибирає реалізацію за `os.name`. На Windows працює `WindowsWindowPlatformAdapter`; на macOS і Linux зараз залишається стандартне системне оформлення. Для майбутніх платформ можна додати нову реалізацію адаптера й зареєструвати її у фабриці, не змінюючи `MainWindowController` або редактор.

Створення `WindowsWindowPlatformAdapter` не завантажує `user32`. Нативна прив'язка через JNA створюється лише всередині `install(...)` після перевірки показаного `Stage`, коли адаптер справді під'єднується до Windows-вікна. Тому фабрика може перевіряти вибір Windows-платформи на Linux або macOS без спроби завантажити Windows-бібліотеку.

## Збереження нативної поведінки Windows

Адаптер працює з HWND показаного Stage через JNA й не використовує внутрішні або інкапсульовані API JavaFX. Він прибирає стиль системного заголовка, залишаючи нативні стилі системного меню, мінімізації, максимізації та зміни розміру. Для `WM_NCCALCSIZE` клієнтська область займає весь прямокутник вікна. Для `WM_NCHITTEST` семантична область перетворюється на нативний код Windows:

- `HTCAPTION` — вільна область заголовка, тому Windows керує перетягуванням і системним прилипанням;
- `HTMAXBUTTON` — кнопка максимізації/відновлення, потрібна для меню Snap Layouts у Windows 11;
- `HTMINBUTTON` і `HTCLOSE` — кнопки згортання та закриття;
- `HTLEFT`, `HTRIGHT`, `HTTOP`, `HTBOTTOM` і коди кутів — штатна зміна розміру й системний курсор.

Обробник нативних повідомлень передає решту повідомлень початковій процедурі вікна JavaFX Glass. Нативні команди кнопок делегуються через `WindowChrome`, а далі до `MainWindowController`, щоб зберегти один шлях роботи з `Stage` та завершення редактора. Розмір і позиція й надалі зберігаються через наявний `WindowStateStore`.

Англійська є базовою мовою набору підписів заголовка: `src/main/resources/i18n/windowChrome.properties`. Основні повідомлення застосунку так само використовують англійський базовий файл `src/main/resources/i18n/messages.properties`. Для цих наборів не потрібні дублікати `windowChrome_en.properties` і `messages_en.properties`: `LocalizationService` завантажує базовий ресурс при виборі англійської мови. Варіанти з суфіксами локалей призначені для перекладів, наприклад `_uk` і `_ru`.

`WindowChromeView` отримує доступні назви кнопок через спільну `LocalizationService`; вони оновлюються разом з активною мовою. Служба локалізації нормалізує англійську до `Locale.ROOT`, а для інших мов використовує стандартну ієрархію ресурсів із базовим файлом як резервним рівнем. Власні JavaFX `Tooltip` на кнопках не встановлюються, щоб не конфліктувати з нативними підказками Windows. `WindowChromeView.dispose()` відписує слухачів під час закриття, щоб не утримувати вікно після завершення.

`WindowHitTestCalculator` перевіряє геометрію лише за типізованим незмінним знімком та не залежить від JavaFX, JNA або кодів конкретної ОС. Він визначає кнопки заголовка перед зонами resize: це зберігає клікабельність кнопок навіть там, де їхні прямокутники геометрично перетинаються з тонкою смугою зміни розміру. Для звичайних точок resize-краї та кути мають пріоритет над вільною областю заголовка й клієнтським вмістом. Обчислення й граничні випадки покриті unit-тестами в пакеті `window`; відповідність логічних областей протоколу Win32 перевіряється окремими тестами в `windowing`.

Якщо під'єднання Win32 не вдається, застосунок записує попередження й переходить на `JavaFxWindowPlatformAdapter` із переміщенням і ручною зміною розміру. Резервний адаптер слухає події кореня сцени та визначає область натискання через той самий `WindowHitTestCalculator` і знімок `WindowChrome`. Він лише перетворює семантичний результат на переміщення, resize або вибір курсора, тому не дублює геометричні пороги й не залежить від CSS-класів кнопок. Граничний тест перевіряє, що натискання на верхньому краї кнопки не запускає resize навіть тоді, коли вузол події не має CSS-класу кнопки. Це не повний еквівалент нативної поведінки: Snap Layouts та всі ефекти Windows у ньому не гарантовані. На macOS і Linux власний заголовок наразі не вмикається.

## Перевірка на Windows

Після додавання залежностей JNA запустіть повний набір тестів, а потім застосунок на Windows 10/11. Вручну перевірте згортання/відновлення, закриття, подвійне клацання по заголовку, перетягування на інший монітор, прилипання до кожного краю, Snap Layouts наведенням на кнопку максимізації, resize кожного краю й кута, максимізацію подвійним клацанням, а також збереження геометрії під час завершення. Особливо перевірте конфігурації масштабування екрана (100%, 125%, 150%) і вікна на кількох моніторах.
