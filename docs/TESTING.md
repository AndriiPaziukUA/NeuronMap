# Тестування NeuronMap

Автоматизовані тести містяться в `src/test/java/com/example/neuronmap/`. Підпакети тестів відповідають підпакетам production-коду там, де код тематично розділений. Під час зміни компонента спочатку запускай найближчі тести, а перед передаванням змін — повний набір.

## Команди

Запуск усіх тестів, побудова звіту покриття та перевірка встановлених quality gates:

**Windows PowerShell**

```powershell
.\mvnw.cmd clean verify
```

**Linux/macOS**

```bash
./mvnw clean verify
```

Якщо Maven установлено окремо, можна виконати `mvn clean verify`. Команда `clean test` запускає тести, але не виконує JaCoCo-перевірку, яка прив'язана до фази `verify`.

GitHub Actions workflow `.github/workflows/ci.yml` запускає `clean verify` на кожному push до будь-якої гілки, у pull request до `dev` і вручну. Матриця перевіряє Windows, Linux (із Xvfb для JavaFX-тестів) та macOS на JDK 25. JaCoCo перевіряє мінімальні пороги покриття пакета: 80% інструкцій, 80% рядків, 60% гілок і 80% методів. Окремий job статичного аналізу генерує повний PMD XML-звіт і перевіряє відбитки нових знахідок високого пріоритету проти `quality/pmd-baseline.json`. Quality gate блокує CI лише через нові або збільшені знахідки PMD пріоритетів P1–P2. Знахідки P3–P5 залишаються у повному звіті як рекомендації та не блокують звичайні коміти. Помилки читання звіту, некоректні пріоритети та несумісність версії PMD із baseline залишаються блокувальними, щоб перевірка не могла тихо пропустити некоректні дані. Звіт публікується як artifact CI. Перевіряльник baseline має власні автоматизовані тести в `quality/test_check_pmd_baseline.py`. Коли додаєш або змінюєш workflow, перевір реальний запуск у вкладці **Actions** репозиторію; локальний запуск не замінює результат CI. Створення гілки без нового push не запускає перевірку, оскільки CI перевіряє код під час push або pull request.

Окремий клас:

```bash
./mvnw -Dtest=NeuronServiceTest test
```

Регресійні тести життєвого циклу подань:

```bash
./mvnw -Dtest=MapPresentationWorkflowLifecycleTest test
```

Кілька класів:

```bash
./mvnw -Dtest=NeuronServiceTest,SimulationSessionTest test
```

У Windows використовуйте `.\mvnw.cmd` замість `./mvnw` (без пробілу на початку команди). Maven Compiler налаштований на JDK 25. Проєкт використовує JavaFX 27; JavaFX-тести запускають toolkit і виконують перевірки графічних вузлів у JavaFX Application Thread. Допоміжний `JavaFxTestSupport` централізує запуск toolkit, синхронне виконання дій у JavaFX-потоці та передавання помилок у JUnit. Для цих тестів має бути доступне середовище з потрібними JavaFX native-залежностями.

JaCoCo формує звіт у `target/site/jacoco/` на фазі `test`. На фазі `verify` виконується окрема перевірка порогів; вона блокує збірку, якщо загальне покриття пакета опускається нижче 80% інструкцій, 80% рядків, 60% гілок або 80% методів. CI завантажує звіт як artifact `jacoco-coverage`, щоб можна було дослідити покриття конкретних класів.

## Інкрементальна перевірка PMD

Запуск тієї самої перевірки, яку використовує CI, після генерації PMD XML-звіту:

```bash
./mvnw --batch-mode test-compile pmd:pmd
python3 -m unittest discover --start-directory quality --pattern 'test_*.py'
python3 quality/check_pmd_baseline.py --baseline quality/pmd-baseline.json --report target/pmd.xml --max-priority 2
```

Параметр `--max-priority 2` означає, що quality gate порівнює з baseline лише знахідки P1 і P2; нижче числове значення PMD означає вищу критичність. Параметр можна змінити від 1 до 5 для окремого запуску, але типове значення — 2. Повний PMD XML не фільтрується: усі знахідки залишаються доступними в HTML/XML-звіті для планового очищення технічного боргу.

Baseline зафіксовано зі звіту PMD 7.17.0 для commit `c8f9bb2511723d0569a68824a90d97662f399f35`; він містить 3002 відбитки у 593 парах «файл + правило». Baseline навмисно зберігає повний набір відомих знахідок, тоді як quality gate фільтрує поточний звіт до P1–P2 перед порівнянням. Завдяки цьому старі знахідки P1–P2 залишаються дозволеними, а нові чи збільшені знахідки P3–P5 не блокують робочі коміти. Для кожної знахідки відбиток SHA-256 враховує шлях до файла, правило, набір правил, пріоритет, пакет, клас, метод, координати стовпців і нормалізований опис. Номери рядків навмисно не входять до відбитка, тому вставлення рядків вище за незмінене порушення не створює помилкового приросту.

Якщо з'являється новий відбиток або збільшується кратність того самого відбитка P1–P2, CI блокується. Зменшення кількості знахідок не змінює baseline автоматично. Оновлювати baseline слід окремою перевіреною зміною після аналізу поточного звіту; оновлення baseline не виправляє зафіксовані ним порушення, а лише визначає поточний набір відомих знахідок, після якого перевіряється приріст. Оновлення версії PMD вимагає свідомого перегляду baseline, оскільки інша версія рушія може змінити набір знахідок.

## Каталог тестів

Наведений перелік описує основні тестові класи й сценарії перевірок репозиторію. Описи вказують на основні сценарії кожного класу, а не на вичерпний список окремих методів усередині нього.

### `testsupport`

- `JavaFxTestSupport` — одноразовий запуск JavaFX toolkit, синхронне виконання дій у JavaFX Application Thread і передавання помилок до JUnit.
- `TransientRepositoryTestSupport` — створення відкладеного репозиторію в ізольованому тестовому каталозі з явним коренем володіння для перевірки матеріалізації.

### `app`

- `NeuronMapAppTest` — вибір початкового проєкту та перевірки життєвого циклу вікна: послідовність збереження геометрії й завершення редактора, одноразове виконання та збереження первинної помилки при кількох збоях.
- `MainWindowControllerTest` — контракт і життєвий цикл головного вікна: передавання перевіреної конфігурації, незалежність від фасаду редактора, делегування оформлення до `WindowChromeLifecycle`, одноразове завершення та очищення оформлення під час помилки завершення редактора.
- `WindowChromeLifecycleExtendedWindowTest` — єдиний шлях оформлення через `StageStyle.EXTENDED` і `HeaderBar`, системні ролі кнопок, виключення інтерактивних кнопок із перетягуваної області та явна відмова, коли `EXTENDED_WINDOW` не підтримується.
- `NeuronMapEditorTest` — контракт прикладного фасаду життєвого циклу редактора й перевірка, що він не утримує файлову інфраструктуру.

### `application`

- `DemoMapFactoryTest` — створення демонстраційної карти.
- `EditorStateTest` — режими редактора, вибір об'єктів і скидання стану.
- `EditorStateCameraValidationTest` — відхилення некоректних значень камери конструктором і сетерами зі збереженням попереднього стану.
- `InitialProjectInitializerTest` — початкове наповнення лише порожнього тимчасового проєкту; збережені та вже заповнені проєкти не змінюються.
- `NeuronMapApplicationServiceTest` — надання служб і передавання операцій відповідним компонентам.

### `config`

- `AppConfigLoaderTest` — читання XML-конфігурації, перевірка допустимості параметрів, безпечне відхилення шляхів поза сховищем і діагностика невідомих ключів у необов'язкових джерелах перевизначень.

### `controller`

- `CameraControllerLifecycleTest` — ідемпотентне звільнення фільтрів камери, перенесення відстеження курсора між сценами та скасування відкладеного збереження.
- `CameraControllerZoomFormattingTest` — форматування відсотка масштабу через спільний форматтер за системної локалі з комою як десятковим роздільником.
- `CameraControllerPanSaveTest` — перевіряє, що натискання полотна без переміщення не зберігає камеру, а фактичне панорамування планує збереження.
- `ConnectionControllerLifecycleTest` — від'єднання фільтрів полотна, скасування прев'ю створення зв'язку та повернення стану редактора до режиму очікування під час повторного безпечного `dispose()`.
- `ConnectionControllerMouseInteractionTest` — перевірка кнопок завершення режимів зв’язків, панорамування полотна без виходу з режимів створення й видалення та руху кінця прев’ю зв’язку за курсором під час перетягування.
- `ConnectionCreationControllerTest` — сценарії створення зв'язків і керування їхнім прев'ю.
- `EditorKeyboardControllerTest` — маршрутизація гарячих клавіш і завершення реєстрації обробників.
- `EditorKeyboardSingleStepShortcutTest` — маршрутизація Ctrl+Space лише за дозволу однотактного продовження, захист від автоповтору та збереження стандартної поведінки Space й текстового введення.
- `MainMenuControllerSceneLifecycleTest` — перенесення клавіатурного фільтра між сценами, ідемпотентність повторної установки й `dispose()`, відсутність реакції на старій сцені.
- `MainMenuControllerTest` — навігація меню та життєвий цикл попереднього перегляду, підтвердження й відкату налаштувань; для міжпакетної UI-інспекції використовує тестовий адаптер `MainMenuViewTestAccess` у пакеті `view/menu`.
- `NeuronClipboardControllerLifecycleTest` — перенесення клавіатурних і віконних підписок буфера обміну між сценами, розмежування очищення буфера й `dispose()`, очищення ресурсу під час завершення.
- `NeuronDeletionControllerTest` — видалення нейронів через контролер взаємодії.
- `NeuronDragControllerLifecycleTest` — скасування незавершеного перетягування нейрона без збереження та відновлення курсора.
- `NeuronInteractionControllerMouseButtonTest` — поведінка взаємодії залежно від кнопки миші.
- `NeuronMenuControllerDirectionTest` — вибір напрямку нейрона через його меню.
- `NeuronMenuControllerOverlayHostTest` — перевірка, що координатор використовує явно переданий контейнер накладки та не визначає його обходом дерева JavaFX.
- `NeuronOverlayCoordinateTest` — обчислення координат меню та накладок відносно нейрона.
- `NeuronToolDragControllerLifecycleTest` — видалення обробників джерел перетягування, відновлення попереднього курсора та збереження курсора, який пізніше встановив власник кнопки.

- `SimulationControllerSpeedFormattingTest` — формат швидкості в локалізованому повідомленні після зміни швидкості активної симуляції.

- `SimulationControllerStopSignalsTest` — перевірка, що зупинка сигналів очищує активний runtime-стан та оновлює індикатори без збереження карти.

## Принципи написання тестів

Нові тести мають перевіряти очікувану поведінку, а не повторювати алгоритм реалізації. За потреби включай:

- типовий успішний сценарій;
- граничні та некоректні вхідні значення;
- поведінку під час помилки, особливо там, де потрібно звільнити ресурс або зберегти початковий стан;
- регресійний сценарій, який доводить, що попередній дефект не повернувся.
