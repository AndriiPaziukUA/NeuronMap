# NeuronMap

NeuronMap — настільний застосунок на JavaFX для створення, редагування та симуляції карт нейронів. Карта містить нейрони, напрямлені зв'язки між ними й групи. Можна змінювати параметри та орієнтацію нейронів, переміщати їх, копіювати й вставляти елементи, а також скасовувати та повторювати зміни.

Цей файл описує вимоги до запуску, основні можливості та структуру коду. Докладніший розподіл відповідальностей наведено в [документації архітектури](docs/ARCHITECTURE.md), а список тестів і способи їх запуску — у [документації тестування](docs/TESTING.md).

## Вимоги

- JDK 21.
- Операційна система, на якій доступні JavaFX та потрібні нативні залежності.
- Підключення до мережі під час першого завантаження залежностей Maven, якщо їх ще немає в локальному кеші.

У репозиторії є Maven Wrapper, тому окремо встановлювати Maven зазвичай не потрібно. Переконайся, що команда `java -version` використовує JDK 21.

## Запуск застосунку

Усі команди запускай із кореня репозиторію.

**Windows PowerShell**

```powershell
# Запустити застосунок
.\mvnw.cmd javafx:run

# Запустити повний набір тестів із очищенням попередніх результатів
.\mvnw.cmd clean test
```

**Linux/macOS**

```bash
# Запустити застосунок
./mvnw javafx:run

# Запустити повний набір тестів із очищенням попередніх результатів
./mvnw clean test
```

Якщо Maven установлено окремо, можна використовувати `mvn javafx:run` та `mvn clean test`. JaCoCo формує звіт покриття в `target/site/jacoco/`, якщо збірка дійшла до відповідного етапу.

Окремий тестовий клас можна запустити командою, наприклад:

```bash
./mvnw -Dtest=SettingsEditSessionTest test
```

У Windows заміни `./mvnw` на `.\mvnw.cmd`.

## Можливості

- Створення й редагування карти нейронів із напрямленими зв'язками та групами.
- Переміщення, вибір, обертання та зміна напрямку нейронів.
- Копіювання й вставлення нейронів і груп.
- Симуляція поширення сигналів із керуванням запуском, паузою та швидкістю.
- Скасування й повторення змін карти.
- Окремі проєкти з локальним збереженням у SQLite.
- Каталог проєктів із можливістю створення, відкриття, перейменування та видалення.
- Англійський, український і російський інтерфейси.
- Попередній перегляд налаштувань у меню з можливістю підтвердити зміни або відкотити їх без постійного збереження.
- Власне оформлення головного вікна на Windows із нативним переміщенням, зміною розміру та підтримкою Snap Layouts у Windows 11.

## Оформлення головного вікна

На Windows застосунок використовує власний заголовок вікна та зберігає нативну поведінку системних кнопок, переміщення, зміни розміру й Snap Layouts. На Linux і macOS використовується стандартне оформлення вікна операційної системи.

Фабрика платформних адаптерів може створити Windows-адаптер без завантаження `user32`. Прив'язка до Win32 через JNA відбувається лише під час `install(...)` для показаного Windows-вікна, тому перевірка вибору платформи не залежить від ОС, на якій запускається тест. Геометрія та контракт взаємодії заголовка винесені в JavaFX- і платформонезалежний пакет `window`. Докладніше див. [опис власного оформлення вікна](docs/WINDOW_CHROME.md).

## Структура коду

Код застосунку розміщений у `src/main/java/com/example/neuronmap/`, ресурси — у `src/main/resources/`, тести — у `src/test/java/com/example/neuronmap/`. Вкладені пакети групують класи за тематичною відповідальністю, а не створюють додаткові архітектурні шари.

| Пакет | Відповідальність |
|---|---|
| `app` | Точка входу, створення залежностей і життєвий цикл головного вікна. |
| `application` | Стан редактора, доступ до прикладних служб і сценарій початкового наповнення нового тимчасового проєкту. |
| `config` | Читання й перевірка конфігурації запуску. |
| `controller` | Обробка подій UI та передавання дій до служб і координаторів. |
| `coordinator` | Послідовність взаємодії кількох компонентів редактора або сценарію проєкту. |
| `i18n` | Активна локаль, переклади й контракт збереження вибраної мови. |
| `model` | Дані карти, нейронів, зв'язків, груп і стану представлення. |
| `persistence` | Спільні контракти репозиторіїв і `PersistenceException`. |
| `persistence/map` | Сховище тимчасового проєкту. |
| `persistence/project` | Файловий каталог проєктів, спостереження за каталогом і визначення каталогу збереження. |
| `persistence/settings` | Глобальні налаштування та збереження вибраної мови. |
| `persistence/sqlite` | З'єднання, схема, читання й запис даних проєкту в SQLite. |
| `persistence/window` | Модель та файлове сховище геометрії вікна. |
| `project` | Типи та описи проєктів. |
| `service` | Операції над моделлю, картою, каталогом проєктів і історією. |
| `service/history` | Знімки стану, скасування та повторення змін. |
| `settings` | Спільний типізований життєвий цикл попереднього перегляду, підтвердження й відкату налаштувань. |
| `simulation` | Обчислення тактів і поширення сигналів без залежності від JavaFX. |
| `util` | Незалежні від UI математичні, координатні й числові допоміжні операції. |
| `window` | Платформонезалежний контракт оформлення вікна й геометрія інтерактивних областей без залежності від JavaFX чи ОС. |
| `windowing` | Інтеграція заголовка з платформними API та перетворення областей на коди конкретної ОС. |
| `view/connection` | Подання та графічна геометрія зв'язків. |
| `view/editor` | Основне полотно, сітка, панель інструментів і керування порядком графічних шарів. |
| `view/group` | Графічне представлення груп. |
| `view/menu` | Сторінки меню, список проєктів, вибір мови та діалоги. |
| `view/neuron` | Подання нейрона, його меню, налаштування, геометрія й накладки. |
| `view/simulation` | Подання та анімації результатів симуляції. |
| `view/status` | Рядок стану та життєвий цикл повідомлень. |
| `view/support` | Спільні JavaFX-допоміжні компоненти, підказки, пошук вузлів і часові параметри UI. |

## Основні архітектурні правила

- `model` і `simulation` не залежать від JavaFX.
- `view` відображає стан і передає дії через callback-и, але не виконує бізнес-операції та збереження.
- `controller` обробляє взаємодію користувача; правила моделі та збереження належать відповідним службам і `persistence`.
- `coordinator` потрібен для узгодженої послідовності дій кількох компонентів, а не для дублювання логіки служб.
- `MapPresentationCoordinator` є власником синхронізації подань карти з моделлю.
- `ProjectWorkflowCoordinator` координує операції над проєктами, а `EditorProjectSessionCoordinator` — підготовку та активацію редакторської сесії.
- Спільна логіка має одного відповідального власника; нові абстракції додаються лише за реальної потреби.

## Як працює попередній перегляд налаштувань

`MainMenuController` використовує єдиний `settings.SettingsEditSession`. Кожен параметр реєструється через три callback-и: отримання поточного значення, тимчасове застосування й постійне збереження. Коли користувач змінює параметр, нове значення застосовується для попереднього перегляду, але не записується у сховище.

Під час підтвердження сесія зберігає змінені параметри. Під час скасування вона повторно застосовує початкові значення у зворотному порядку реєстрації. `MainMenuController.registerSetting(...)` та `previewSetting(...)` дають змогу підключати наступні параметри до цього самого життєвого циклу. Нові параметри потрібно реєструвати до початку активної сесії редагування.

Відкат намагається відновити всі параметри, навіть коли callback одного з них завершується помилкою. Постійне збереження кількох параметрів не є атомарною транзакцією: помилка під час пізнішого запису не скасовує автоматично попередні успішні записи.

## Де зберігаються дані

Каталог даних визначається через домашній каталог користувача та шлях `Documents/NeuronMap`. Збережений проєкт має власну папку з файлом `project.db`. Каталог проєктів формується за вмістом файлової системи; проєкт без бази даних не вважається збереженим.

Загальні налаштування застосунку зберігаються окремо у `global.properties`, а геометрія головного вікна — у файлі, визначеному конфігурацією (типове ім'я — `window.properties`). Налаштування карти, зокрема камера та тривалість такту симуляції, зберігаються через активний контракт `MapRepository`.

Порожній новий проєкт може залишатися тимчасовим у пам'яті, поки не з'явиться потреба в постійному збереженні.

## Як змінювати код

1. Перевір актуальний стан потрібної гілки та прочитай відповідні розділи `docs/ARCHITECTURE.md` і `docs/TESTING.md`.
2. Знайди наявний компонент із потрібною відповідальністю, перш ніж створювати новий.
3. Зберігай напрямок залежностей між шарами та не дублюй наявну логіку.
4. Додавай тести для звичайних, граничних і регресійних сценаріїв.
5. Запускай `clean test` через Maven Wrapper.
6. Перевір, чи відображають документація та JavaDoc фактичну реалізацію.

Опис конкретного API шукай у JavaDoc біля відповідного класу й методу. Тести в `src/test/java` є прикладами перевірки очікуваної поведінки.
